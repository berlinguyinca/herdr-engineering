# Service metadata observer

The observer adds current process ownership and Git provenance to services that
the fabric agent has already registered, and discovers verified native-owned
applications on dynamically allocated ports. It leaves the fabric agent, its
forwarders, and native Herdr/Pi sessions running. Restarting the old fabric
agent can interrupt forwarded TCP/WebSocket streams; it is unnecessary for
metadata rollout.

Run on each service's owning host from an isolated installation of the current
HerdR Engineering wheel:

```sh
python -m herdr_engineering.service_metadata_feed --once --dry-run
python -m herdr_engineering.service_metadata_feed --loop 30
```

The dry run reads local listener/process evidence, the existing
`~/.local/share/herdr-engineering/state/fabric-agent.json`, and the control
plane's service inventory. It prints counts of mapped, owned, Git-linked,
unconfirmed and unmapped records, with errors/truncation visible. It sends no
observations. The observer never constructs a fabric agent, binds forwarding
sockets, registers leases or writes the existing state file. Existing fabric
services receive metadata only: their health, routes, ports and lifecycle
timestamps remain under the existing reporter's authority.

Unregistered listeners with positive native ownership proof become separate
control-plane observations, including ports above 32768. Their stable IDs bind
host, PID, process birth identity and source port; port reuse creates a distinct
physical instance and retains the old record's history. These observations
have `endpoint_scope: local_only`, `url: null`, and no shared route or proxy.
The UI can show the local port and owning session without implying remote
access. Browser debugging listeners using `--remote-debugging-port` (including
port zero) are excluded; inaccessible or truncated command evidence also
prevents a new advertisement. Arguments never enter payloads or logs.

Only a complete successful listener scan can mark an observer-owned instance
missing. Ambiguous or inaccessible PID evidence cannot prove disappearance.
Missing observations retain ownership history and indicate unknown availability;
they do not claim an application was stopped. Existing legacy services remain
metadata-only regardless of observer-owned lifecycle updates.

Mapping requires the exact existing control-plane host, service label and
source port. A port or cwd alone never proves ownership. Ownership comes from
native pane identity and fresh PID/start-time ancestry; Git metadata comes
from that verified listener's local checkout. Ambiguous or inaccessible
listeners produce an unconfirmed observation, retaining historical origin.
A verified replacement PID/start identity without ownership explicitly clears
the old live ownership. The backend preserves metadata across legacy agent
heartbeats that omit these fields.

Each pass has a 20-second collection budget, a 10-second publication budget,
at most 256 registered entries,
and bounded state/API reads (4 MiB, 4096 records). Partial batches rotate fairly.
Owned/system observations refresh every 45 seconds or upon change (at most
60 seconds with the 30-second loop); unassigned/missing observations publish
only on change. The last-sent cache holds at most 512 records. Failed writes
remain eligible for retry. No notifications are generated by this companion.

The systemd template is `deploy/mission-feed/herdr-service-metadata.service`.
Install a dedicated wheel/venv under an immutable release in
`~/.local/share/herdr-service-metadata/`, with `current` pointing to it. Do not
upgrade the shared global Herdr Engineering venv. The template preserves the
existing `fabric.env` and accepts additional private settings in
`~/.config/herdr-engineering/service-metadata.env` (mode `0600`):

- `HERDR_ENGINEERING_CONTROL_PLANE_URL` or `HERDR_CP_URL`: control-plane URL.
- `HERDR_SERVICE_METADATA_HOST`: an explicitly verified existing host ID.
- `HERDR_ENGINEERING_STATE`: existing fabric state directory, when overridden.
- `HERDR_CP_API_KEY`: optional control-plane credential; alternatively set
  `HERDR_SERVICE_METADATA_API_KEY_FILE` to a private credential file.

Explicit CLI overrides are `--control-plane`, `--host-id`, `--state-file` and
`--api-key-file`; credentials themselves never appear in arguments or logs.
HTTP redirects are rejected. On macOS, use a separate launchd companion with
the same module command and private environment configuration. Activate only
after the receiving backend supports `service.metadata` and
`service.listener_observed`, then verify API
observations and that existing fabric/native/mission/session collector PIDs
are unchanged. Offline hosts remain pending until they can be verified.
