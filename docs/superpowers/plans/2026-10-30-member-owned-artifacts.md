# Member-owned artifacts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship plan 5 of 5 (spec section E, as amended by the operator on 2026-10-30): signed-in group members create, publish, version, share (lab **or public**) and delete their own artifacts, both from the artifact skill (collaboration MCP server) and from a small "My artifacts" web UI at the configured artifacts host (`artifacts.metabolomics.us`). A member may share any artifact on which they hold the existing `share` permission, under the same rules as the operator path. Storage is not capped by default; usage is accounted per member and visible to the operator.

**Architecture:** One transport-neutral member service (`artifact_member_service.py`, in `collab-public`) backs both the member MCP tools and the member web API, so the two behave identically. Every write becomes an intent on plan 3's intents queue, carrying an **actor** (a collab agent or a signed-in Cognito user). The control-plane worker re-checks membership, the artifact permission (`ArtifactStore.report_permission`, the same owner-or-grant rule the operator share routes use through `_access`) and any configured limit against Postgres and applies it as principal `member:<user_id>`. File bytes use plan 3's chunk staging protocol unchanged (`collab_bridge_files`: fixed `CHUNK_BYTES`, derived `upload_id_for`, `validate_chunk`, `link_new_bytes`, worker-side streaming assembly verified against the declared sha256 and size, `sweep_staging`), staged under a per-member owner key so an upload resumes across MCP and web; staging is collab-side only, and the worker assembles at publish inside the member's lane, so multi-GB uploads do not ride the 60 s intent clock. Shares created by members go through the existing `ShareStore` / `approve_share` path unchanged in semantics (pinned version, expiry, two-step create → confirmed approve, revocable), with member-specific caps, rate limits, audit and a "Shared by" banner. The web UI is plain DOM served by `collab-public` on the artifacts host; sign-in reuses PR #486's lab sign-in with a separately domain-tagged session. The operator gets a Members panel that sees and can revoke every member-created link.

**Tech Stack:** Python 3.12 / asyncpg, collab MCP (JSON-RPC over HTTP), Postgres migrations in `deploy/control-plane/migrations`, plain ES-module web (`packages/`), node:test + Playwright, nginx collab edge (`deploy/control-plane/collab-edge`); POSIX sh + Python client in the separate `herdr-artifacts` repo.

**Spec:** `docs/superpowers/specs/2026-10-30-artifact-sharing-gui-and-collaboration-design.md` — section E, "Second builder check: resolutions", "Builder-check resolutions", "Delivery order" item 5, **as amended by the operator decisions of 2026-10-30 below** (Task 16 updates the spec text). Share-link rules: `docs/superpowers/specs/2026-10-30-artifact-share-links-design.md`; lab sign-in and approval as built in PR #486 (`artifact_share_api.py`, `share_public.py` `_session`, `share_session.py`, `share_lab.py`, `share_static/share.js`). Plans 1–2: `docs/superpowers/plans/2026-10-30-artifact-share-panel-and-merge-engine.md` (merged on this branch: `merge_commit`, migration 0043).

## Decisions (operator, 2026-10-30 — binding)

* **D1 No storage caps by default.** The spec's 25 MiB/artifact, 200 MiB/member and 20 artifacts/member are removed (storage is hundreds of TB). Usage **accounting** stays (bytes, artifact and version counts per member, shown to the operator and to the member). Limits exist only as optional YAML values defaulting to `null` (unlimited), overridable per member by the operator. Anti-abuse rate limits and per-request sanity limits remain, all configurable.
* **D2 Members get a web UI** at the configured artifacts host (`artifacts.metabolomics.us`), signed in with the same Cognito lab login as lab shares: "My artifacts" — list, chunked upload with progress, version history, share (lab or public), list and revoke own links, delete, usage. Plain DOM; the member UI follows the repo-wide rule "no iframe/frame/object/embed anywhere" (operator rule). Supersedes the "members get no web UI" reading. The MCP tools stay on the MCP host and use the same service layer.
* **D3 Members may create public links — reverses spec section E's group-only rule.** A member may create a lab or public link on any artifact where their principal holds the existing `share` permission: their own (`created_by`), or one granted to them with `share` or `admin` in `artifact_acl` (`ArtifactAcl.can` / `ArtifactStore.report_permission`; `read`/`edit`/`review` alone do not include `share`). Same requirements as the operator path: pinned immutable version, expiry (public: default 30, max 90 days, `default_public_days`), revocable, two-step create → approve with `confirm: true` by a `share` holder. PR #486's approval is not operator-only (any `share` holder approves their own share), so no `member_public_links` approval switch is needed; members get `direct` semantics identical to the operator's. Every member public-link create/approve/revoke is audited with the member principal. Members list and revoke their own links; the operator sees and can revoke any. Anonymous/public visitors get no edit or annotation rights (unchanged).
* **D4 (Q1/Q-D)** The operator has **read** and **share** (not edit/commit) on member-owned artifacts and may create lab or public links on them.
* **D5 (Q2)** Members can delete their own artifacts: soft delete = retract (`record_retraction`) + revoke the artifact's live links + abort open uploads + tombstone in the member's list; the UI asks for confirmation. Only the operator can purge (remove bytes), with explicit confirmation.
* **D6 (Q3)** Disabling a member (directory status `disabled`, left the group, or sharing disabled by the operator) revokes the live links they created.
* **D7 (Q4)** Usage counts all stored versions (and soft-deleted artifacts until purged, reported separately).
* **D8 (Q-A)** Member-created shares get their own caps, `control_plane.collab.members.share_limits: {max_share_bytes: null, max_total_bytes: null}` (null = unlimited). The global `control_plane.share.max_share_bytes` / `max_total_bytes` keep their values and apply to operator-created shares only.
* **D9 (Q-B)** The old host's (`localdev.mcp.metabolomics.us`) `/s/` is simply replaced: share links live on the new share host (`share.public_host`) only. No redirects and no legacy compatibility (the project is alpha and no links have been issued).
* **D10 (Q-C)** Default per-file upload limit is 1 TiB (`request_limits.max_upload_bytes: 1099511627776`), configurable; `null` = only the structural bound.

## Global Constraints

* **Share permission is the gate.** A member creates, approves, lists or revokes links on an artifact only if `report_permission(artifact_id, member_principal, "share")` is true at the time the worker applies the intent (and, defense in depth, inside `ShareStore.create`/`mark_live`). Denial is non-disclosing `not_found`. Audience `public` or `lab` both allowed; the member lab rules below still apply to `lab`.
* Member principal: `member:<collab user_id>` where `user_id` is the Cognito `username` claim, falling back to `sub`, as `CognitoAuthenticator.verify_claims` does — for an agent, its collab owner; for a web session, the signed-in user. One function (`member_principal`, Task 1) is the only derivation. Ownership = the existing `artifacts.created_by`; no `owner_principal` column. `collab:` principals (plan 3 grant collaborators) still never create shares (plan 3 rule, unchanged).
* A member is an **actor** (`{"kind": "agent", "agent_id"}` or `{"kind": "user", "user_id"}`) whose user is approved, non-disabled and in `collab.cognito_group`, and not sharing-disabled (share actions only). An agent actor must also be active and **not external**; external agents are never members.
* **Storage limits (D1):** `control_plane.collab.members.limits: {max_artifact_bytes: null, max_member_bytes: null, max_artifacts: null}` — `null` = unlimited, the default; a set value is a positive integer. Per-member overrides in `artifact_member_usage` (NULL = inherit). Accounting always runs.
* **Share limits (D8):** `members.share_limits: {max_share_bytes: null, max_total_bytes: null}` — checked in `approve_share` for member-created shares, against the total of live member-created shares; operator-created shares keep the global caps against the operator-created total.
* **Chunk protocol (plan 3, imported, not configurable):** `CHUNK_BYTES = 524_288` raw, base64 on MCP, `MCP_UPLOAD_MAX_BODY = 786_432`, `MAX_CHUNK_INDEX`, `upload_id_for(owner_key, artifact_id, name, file_sha256, size_bytes)`; same index + same sha → replay success, different sha → 409; whole-file sha256 and size verified at assembly. Member owner key: `member_owner_key(principal) = "m_" + sha256(principal)[:24]` — used where plan 3 uses `agent_id` in `staging_path`/`upload_id_for`, for both agent and web actors of the same user.
* **Sanity limits (configurable, `members.request_limits`):** `max_upload_bytes: 1099511627776` (1 TiB per file; D10; passed to `validate_chunk` as the member `max_file_bytes`), `http_chunks_per_request: 32` (a web PUT carries a run of up to 32 consecutive chunks = 16 MiB), `max_publish_files: 200`, `max_message_chars: 500`. (Over MCP a 1 TiB file is ~2 M chunks; at 1,200 chunks/min that is ~29 h — the skill points to the web UI for large files.)
* **Rate limits (configurable, `members.rate_limits`):** `chunks_per_minute: 1200` (MCP; web runs count 32 each, i.e. ~10 MiB/s per member on either channel), `writes_per_minute: 30`, `share_creates_per_hour: 60`, `session_exchanges_per_minute: 10` (per user), through `CollabService._throttle`.
* **Staging (configurable, `members.staging`):** `bytes_per_member: 1099511627776` (reserved by declared size, like plan 3's `staging_bytes_per_agent`; ≥ `max_upload_bytes` so one maximal file fits), and the shared volume cap is plan 3's `staging_bytes_total` (one volume, one cap). TTL is plan 3's `staging_ttl_seconds`. Over a cap → `429 "upload backlog full; retry"` (backpressure, not a quota).
* Member **lab** shares: `allow_groups ⊆ {collab.cognito_group}`; every `allow_emails` entry is a known pool user's email (code `member_audience_refused`). Lab expiry 1–3650 days, optional; public as the operator (default 30, max 90). Summary → explicit approve with `confirm: true`.
* Content types: the share rules (HTML, PDF, HTML + parquet); same bundle scanner and sandbox CSP. Every link **created by a member** (lab or public) shows "Shared by <name> — content was not reviewed by the operator". Visitors get read-only views; no edit or annotation for public visitors (unchanged).
* **Audit:** every member share create/approve/revoke (lab and public) writes an `artifact_member_events` row with the member principal, actor, artifact, share id, audience and outcome, besides the existing share events.
* Intents expire after 60 s (plan 3); a disabled/removed member's pending intents are rejected; revocation takes effect within seconds, not instantly. Staged parts are not intents and have their own orphan sweep.
* Approve URL travels back once: a 0600 result file readable only by worker and `collab-public`, deleted on first read, swept after 60 s; never logged, never in the event log, never in the mirror or member view.
* **Host and sessions:** new key `control_plane.share.public_host` (bare DNS name, e.g. `artifacts.metabolomics.us`; no scheme/port/path) — the host of new share links *and* of the member UI. Member sessions are signed with `control_plane.collab.members.session_secret` (≥ 32 bytes, YAML only, never printed), domain tag `herdr-member-session-v1`, so a share session can never be replayed as a member session or back. Configuration is YAML only; no new environment variables (operator rule).
* No `iframe`, `frame`, `object` or `embed` in any new or touched page (lint test, Task 12).
* Migration: `0047_member_artifacts.sql` (0043 is on this branch; 0045/0046 are reserved for plans 3/4). If main has moved past, take the next free number at implementation time.
* Python style as surrounding code (`from __future__ import annotations`, asyncpg conn in stores, `ArtifactError`/`ShareError`, hand-validated MCP args with `additionalProperties: False`). Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

* **Cross-member access:** member A naming member B's `artifact_id`/`share_id`/`upload_id` in any tool, web route or intent — or staging a part under B's upload — gets the same non-disclosing "not found" as a nonexistent id, never B's metadata, unless A holds `share` (sharing) or `read` (listing) on it through a grant. Test per tool and per route (Tasks 4, 6, 7, 11).
* **Share permission boundary:** a member with only `read`, `edit` or `review` on someone else's artifact cannot create, approve or revoke a link on it (lab or public); with `share` or `admin` they can; a grant that expires or is revoked between create and approve makes the approve fail and leaves no bundle (Tasks 2, 7).
* **Large upload integrity and resume:** an upload interrupted mid-way resumes (same derived `upload_id`, also across MCP ↔ web) from the missing chunk ranges without re-sending stored chunks; a replayed chunk is a no-op; a chunk with a different sha256 → 409; a web run whose `X-Run-SHA256` mismatches stages nothing; a whole-file sha256/size mismatch at assembly rejects the publish and removes staging; staging over a cap → 429 and nothing is lost; member staging dirs survive plan 3's sweeper while the member is valid and are swept after TTL or when the member is disabled (Tasks 4, 6, 11, 12).
* **Session confusion:** a share-viewer session presented to the member API (and the reverse) is refused; a token from a non-group user, an expired token, or a missing `X-Id-Token` → 401 with no detail; member POSTs from another origin → 403 (Tasks 11, 15).
* **Disabled member mid-flight / delete:** a member removed from the group, sharing-disabled, or whose agent is revoked between append and apply — the intent is rejected and audited, no version/share is created, staged parts are deleted, live links they created (public included) revoked; a soft-deleted artifact accepts no upload, publish or share and its links are gone (Tasks 4, 9).

### Task 3: Usage accounting and optional limits

**Files:** Create `herdr_engineering/control_plane/artifact_member_quota.py`; Test `tests/control_plane/test_artifact_member_quota.py`. (`artifact_uploads.py` is not touched: member bytes use plan 3's staging and assembly.)

**Interfaces:**
- Consumes: `MemberStore`, `MemberLimits` (Task 1).
- Counting rule (D7): `bytes_used` = sum of `size_bytes` of distinct `artifact_blobs` in the scope of the member's non-purged artifacts (all versions; dedup within an artifact only); `bytes_retracted` = the part of it on soft-deleted artifacts.
