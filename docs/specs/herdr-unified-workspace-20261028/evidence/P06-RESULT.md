# P06 — Team-first WebUI and persistent visual map: result (partial)

Status: PARTIAL. The Team Map screen for one project and a "Your teams" list page are built, and explicit teams now have a producer; the Home refactor to team cards and the Conversation view are not.

## Built (merged state: see the PR that added this file)
- `packages/team-map-model.js`: the Team Map's logic with no DOM. Groups a Work Graph snapshot project -> issue -> task ->
  deliverables (via `contains` edges, deliverables under what `produced` them), folds noisy execution kinds into a count,
  filters by kind/status/text, maps every edge type to one of the five meanings (coordination, delegation, dependency,
  produced, reviewed), describes the whole map as sentences (the text fallback; historical edges marked "no longer current"),
  gives progress as milestone counts ("1 of 2 tasks done") and never a percentage, and lays nodes out deterministically
  without moving anything already placed (personal > shared > automatic, per node).
- `HerdrClient.workGraphSnapshot / workGraphLayout / saveWorkGraphLayout`: the existing P02 routes, for the view.
- Tests: `packages/herdr-web-components/team-map-model.test.js` (8, including a 4,001-node graph grouped, described and laid out
  under 1.5 s) and one client test.

## Built: the Team Map screen for one project
- `packages/team-map-view.js` + `packages/team-map.css`, route `#/team-map?root=project:<id>` (nav entry "Team map" under Agents, shown only when `/api/v1/health` advertises `unified_workspace_v1`; the route itself is registered in `packages/app.js`, stylesheet linked in `packages/index.html`).
- Renders from `team-map-model.js` unchanged: an SVG picture (columns project / issue / task / agent / deliverable; five line meanings told apart by dash pattern and a legend, earlier relations faded and labelled "no longer current"), milestone counts per project ("1 of 2 tasks done", never a percentage), filters (search, kind, status, show agent sessions and hosts with the folded-away count), an inspector with a link to the existing artifact/session/host/review page, and the written map (the model's text fallback, open by default) that lists everything, including what the picture caps at 300 nodes.
- Keyboard: one tab stop; arrow keys / Home / End walk the nodes; Enter or Space opens details; Alt+arrow moves a node one cell (refused onto another node or off the map). Every node has an `aria-label`; focus ring from `--focus-ring`; targets 44px; colours only from design tokens.
- Layout: shared and personal positions are read with `workGraphLayout`; new nodes are placed incrementally and nothing already placed (saved or drawn earlier in the session) moves. "Save my layout" writes the personal layout through `saveWorkGraphLayout` with the ETag: saved entries are kept verbatim, only moved nodes change, nodes with no saved position are stored where drawn; a stale ETag (412) is refused with "reload, then save again". Shared-default editing has no UI.
- States: not turned on / project not found (the graph routes answer 404 for both; plain message, not an error, and it does not mark the page "unavailable"), 503 unavailable, error, empty project, filters match nothing, truncated snapshot, layout unreadable (map shown, saving hidden).
- Tests: `packages/team-map-view.test.js` (14): real `team-map-model.js`, real `HerdrClient` against a real local HTTP server speaking the graph routes' contract (404 when off, ETag/If-Match on the layout). They cover markup, escaping, filters, caps, placement, moves, the save document, ETag conflicts, the off state.

## Built: explicit teams and the "Your teams" list
**Which rule defines a team.** The spec bundle is silent on how a team is created. `phases/P05.md` has team *templates* (roles, no host pinning) and `contracts/ENTITY_AND_EVENTS.md` asks for "list own teams/rooms"; nothing says who creates a team, what its members are or who may see it. So the fallback rule was used: **a team is created explicitly (operator action) with a name, an optional project link and an optional room link; the members are the room's members when a room is linked.** Consequences, all enforced by the existing visibility predicate and tested:
- A team linked to a room has visibility `room` for that room: its non-guest members see it, nobody else is told it exists (404, empty lists, no name in any list). A team with no room is visible to operators only. A project-only link does not widen that.
- Only an operator key may create, rename or archive (collab roles are not in the graph principal, so "editor" cannot be checked; members get the usual 404). A member-side editor action is a follow-up that needs room roles in the principal.
- Something the spec did not say and the code already did: `project_created` already writes a per-project team (`team:project:<pid>`, `attrs` without `origin`). It stays, is listed too, and cannot be renamed or archived through these routes (only `origin: explicit` teams can). So "nothing produces teams" was true only of explicit teams.
- Archive keeps the entity and its history (status `archived`, not a tombstone); there is no un-archive. Creating the same name with the same links again returns the existing team (`created: false`, even if archived); pass an `idempotency_key` for a second team of that name.

**Server.** `GET /api/v1/graph/work/teams?status=active|archived|all` (default active; paged), `POST .../teams` `{name, project_id?, room_id?, idempotency_key?}`, `POST .../teams/<id>/rename` `{name}`, `POST .../teams/<id>/archive`. All under the existing handler, so off (404) unless `control_plane.unified_workspace.enabled` and 503 without Postgres. A write appends a `team_created|renamed|archived` row to `fabric_events` (entity_type `team`, actor = the key's principal, deterministic event ids) and projects it at once; the worker reads the same row, so a crash between the two is repaired and a rebuild from clean brings every team back (both tested). A room or project that does not exist or is hidden from the caller is a 404; a room of another project is a 400. Code: `work_graph_core._team_ops`, `WorkGraphStore.team_command/list_teams`, `work_graph_service.handle`.

**CLI.** `herdr-eng teams create NAME [--project P] [--room R] [--idempotency-key K] | list [--status active|archived|all] | rename ID NAME | archive ID` (`herdr_engineering/teams_client.py`, same transport, key-by-env-var-name and output hygiene as `artifacts share`; `--json` everywhere). `HerdrClient.workGraphTeams` for the web; the web page only reads (writes are CLI).

**Web.** `packages/teams-view.js` + the `.teams-*` block of `team-map.css`: route `#/teams`, nav entry "Your teams" under Agents, shown only when `/api/v1/health` advertises `unified_workspace_v1`. One link per team to `#/team-map?root=team:<id>`, archived behind a checkbox, states for loading / off / unavailable / error / empty (the empty state names the command), tokens only, native links and checkbox (no custom key handling).

**Tests.** `tests/control_plane/test_work_graph_teams.py` (12, real Postgres + real collab service + real HTTP: create/idempotency, rename/archive, membership and hidden teams for alice/carol/guest/stranger/viewer key, map snapshot reaches room and project, project-only team, bad input, writes refused for non-operators, rebuild from clean parity, worker repair of an unprojected event, keyed door over HTTP, flag off and 503); `tests/control_plane/test_work_graph_teams_cli.py` (3, the CLI against a real server); `packages/teams-view.test.js` (8, real client against a real local HTTP server speaking the route's contract) and one client test. The new server tests were run against the unchanged source first and failed (12 of 12).
