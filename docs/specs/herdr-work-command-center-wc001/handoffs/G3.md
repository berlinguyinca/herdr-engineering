# G3 handoff: PR links for running missions, refs re-read

Branch `feat/wc001-g3-running-mission-prs` (worktree herdr-wc001), stacked on G2 / PR #644. Not pushed.

## Design and why
`outcomes` entries mean "this mission ended with a result" and consumers rely on that, so membership and meaning are untouched. A sibling top-level field `pr_refs` on the same response carries `{mission_key: [{repository, number}]}` for every listed mission (first 500, MAX_SUMMARIES), running included. It comes from the same single bulk `list_pull_requests` read, grouped by exact mission key (`pi:X1` and `X1` never mix), sorted by (repository, number); only missions with a PR appear; a failing read gives `{}` and the list still answers. Same handler, auth and flag wiring. A new endpoint was not needed: the envelope is a plain object and the JS client parses only `body.outcomes`. The per-entry `prs` stays.

Client: `refsFromMissionOutcomes` also reads `pr_refs` (tolerates absent/malformed), dedupes the same mission+PR across both fields; the resolver's ambiguity rule is unchanged (two distinct missions on one PR => ambiguous, no link). Refresh: `mountGithubProjects` takes optional `loadHerdrRefs`; its existing `refresh()` (5 s poll, live events, tab return) re-reads refs at most once per 30 s (`herdrRefsMs`), via the existing `request()` machinery (abort, hidden-tab skip). A failed re-read marks Herdr data partial. Flag off: no loader, no read. No new timers.

## Contract diff
`GET /api/v1/mission-outcomes`: `{outcomes}` -> `{outcomes, pr_refs}` (additive). New Python `mission_outcome.pr_refs_by_mission`. New view options `loadHerdrRefs`, `herdrRefsMs`.
