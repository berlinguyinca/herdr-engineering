# G8: Pi next action, snapshot contract v4, durable activity store (Herdr side)

Branch `feat/wc001-g8-pi-passthrough-durable` (from `docs/wc001-g7-pi-engineering-audit`). Nothing pushed or deployed.

## A. Next action passthrough
- The feed and store already allowlisted `nextAction` / `nextActionAt` (SUMMARY_FIELDS), so the server is a pure passthrough and stores Pi's literal text, including `No further action is scheduled`.
- `packages/work-summary.js` `piNextAction()`: exposes `{text, at?}` only for non-empty text that is not the literal fallback (trimmed, case-insensitive); text capped at 500 chars; `at` only when it parses. Only mission items with a projection get it.
- `session-context.js` renders a `Pi-reported next action` row (`data-next-action`); `overview-view.js` week-card Details adds the same row. Both escape the text. Sessions with no mission never show one.

## B. Consuming contract v4 (additive)
Assumption to confirm with the Pi agent: the three fields sit on each entry of the snapshot's `missions[]` (top level of the mission, not inside `observability`).
- `contractVersion` 3 and 4 accepted (`SUPPORTED_CONTRACTS`); anything else is rejected as before. Absent v4 fields leave behaviour identical to v3.
- Feed (`mission_activity_feed.py`, `_pi_v4_extras`) forwards only `created_at` / `completed_at` (strings, <= 64 chars) and `links` (first 80 entries, keys `kind`, `repository`, `number` only).
- Server (`mission_activity.clean_pi_fields`) validates again: ISO with zone and not in the future (else dropped), `kind` in {issue, pull_request}, `repository` matches `owner/name` pattern, `number` a real positive int (bool, zero, negative, strings dropped), de-duplicated case-insensitively, bounded to `MAX_LINKS = 20`. Malformed entries are dropped one by one; nothing is repaired or inferred. Summaries expose `created_at`/`completed_at` but not `links`.
- `pr_refs_by_mission` merges Pi `pull_request` links with Herdr's PR records keyed by (repository, number); a Pi-only mission (no Herdr mission record) still appears. New `issue_refs_by_mission`, served as `issue_refs` on `GET /api/v1/mission-outcomes` (additive; older clients ignore it).
- `board-links.js` `refsFromMissionOutcomes` emits `type:'issue'` refs from `issue_refs`; `resolveBoardLink` is unchanged: exactly one distinct mission verifies, two is ambiguous, a PR number never verifies an ISSUE card. Dedupe key now includes the type.
- `work-summary.js` adds evidence entries `pi_reported_created` / `pi_reported_completed` (valid timestamps only).
- Why `historyComplete` and G1 coverage are untouched: Pi times are Pi's own claim about missions Pi still reports. They say nothing about missions that left the snapshot, so they cannot prove a week's history is complete (the G1 reasons in `work_weekly.py` still hold). They are not copied to `started_at` / `completed_at` either, so Started/Finished counts do not move.

## C. Durable MissionActivityStore
- Fit: the repo's existing `DurableEventSink` / `fabric_events` and the private-stream hydrate pattern used by host metrics and deployments. No new service, table or migration (recovery SQL loads every entity type other than service/session/host).
- Write: `MissionActivityStore(persist=...)` mirrors each accepted snapshot as `{entity_type:'mission_activity_store', event_type:'MissionActivityStored', entity_id:'pi:MSN-x', payload:{value, received_epoch, observed_epoch, snapshot_epoch}}` through `repo._persist_mission_activity` (same sink path as host metrics). Throttle: at most one row per mission per 30 s, but a connection-state change writes at once. A failing sink is logged and never breaks ingest.
- Read: `import_state` pops the private stream out of the shared event streams and `order`, builds a fresh store and calls `hydrate`. Newest row per mission wins; kept only if within the 24 h retention, not future-dated (>60 s), the projection is <= 128 KB, shape and key/id/source/connection/epochs check out; at most 128 missions (newest). Corrupt, foreign or unknown rows are skipped and counted (one warning line), never fatal. `links` are re-validated on restore.
- Retention: in memory as before; durably, `prune_events_before('mission_activity_store', now - 24 h)` at most once per hour from the persist path (best-effort, retried next hour).
- Rows are append-only (about 2880 per mission per day at the throttle ceiling, each <= 128 KB); the hourly prune bounds storage to 24 h.
