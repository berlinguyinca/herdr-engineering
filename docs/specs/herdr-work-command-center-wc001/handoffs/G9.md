## What changed
1. `pi_snapshot.py` (the CLI one-shot converter used by `herdr ... pi snapshot`; it posts `mission` envelopes to `/api/v1/ingest`): `SUPPORTED` is now {1,2,3,4}. Audit result: it only ever mapped title/status/goal and `observability` fields; it never carried times or links, so v4 maps exactly like v3 and the v4 fields are deliberately NOT added to its envelopes (the feed, `mission_activity_feed.py`, is the path that forwards them; it already accepted 3 and 4). 0, negatives, 5+, None, strings, bool, float, list, dict are still rejected exactly as before.
   - Real v4 golden confirmed against Pi's `mission-snapshot-v4.golden.json`: `created_at`, `completed_at` and `links` are on each entry of `missions[]` (top level of the mission, not inside `observability`). This resolves the G8 assumption. Trimmed copy: `tests/fixtures/pi-snapshot-v4-golden-trimmed.json` (kept: id, revision, title, goal, times, links, status, and a few observability fields).
   - End to end test: golden shape -> real `MissionActivityFeed` collector -> real `ControlPlaneServer` ingest -> HTTP `GET /api/v1/mission-activity` shows `created_at`/`completed_at` (normalised to `+00:00`), and `GET /api/v1/mission-outcomes` gives `issue_refs {pi:MSN-golden-full: org/repo#5}` and `pr_refs {...: org/repo#9}`.
2. `mission-live-view.js` Next action row now goes through `piNextAction` (the same rule as the week card and session context). To avoid an import cycle (work-summary -> mission-catalog-view -> mission-live-view) the function moved unchanged to new `packages/pi-next-action.js`; `work-summary.js` re-exports it, so existing imports and tests are unchanged. Literal (any case, padded), empty, non-string show nothing; text is trimmed and capped at 500 chars.
3. New `tests/control_plane/test_mission_outcomes_pi_refs_http.py`: non-empty `issue_refs`/`pr_refs` from Pi links ingested over real HTTP, merged and deduped with a Herdr PR record, invalid links dropped, two missions sharing an issue, 401 for no/wrong/empty key, and "flag off". Server-side the route has no flag (the work_center flag is a `/health` capability read by the dashboard); the test states that: flag off means the capability is absent and the route still answers with the same additive fields; flag on advertises the capability.
4. New `tests/control_plane/test_mission_activity_postgres.py`: a real PostgreSQL. This repo's existing DB tests use `tests.e2e.pg.ThrowawayPostgres` (a private initdb cluster on a unix socket, binaries from `/usr/lib/postgresql/*/bin`, `pytest.importorskip("asyncpg")`, skip when binaries are missing). PostgreSQL 16 binaries are installed here, so it RAN (no docker, no existing container or volume touched). Write via `DurableEventSink`, restart via `PostgresSource` + `load_into` (production recovery path), read, and prune of a 48 h old row; plus an expired never-pruned row ignored on restart.
5. Playwright (`work-center-real-server.test.mjs`, two new tests) against the real fixture server with new seed `PI_ACTIVITY_SEED=1` in `tests/playwright/server.py` (a v4-shaped Pi snapshot ingested through `IngestService`, plus an agent in `pi:MSN-PI1`): flag on shows `[data-next-action]` "Run the integration suite" in the session Work context and an ISSUE card org/app#321 gets Open in Herdr to `#/missions/pi%3AMSN-PI1` while #322 does not; flag off with the same data shows neither.
