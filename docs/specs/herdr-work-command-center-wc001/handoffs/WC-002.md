## Semantics
- Output per metric `{count, coverage}`; `count` is null when coverage is `unknown`. `open`, `paused_quota`, `attention_needed` are labelled `basis:'snapshot'` with `as_of`.
- `started`/`finished` cap at `partial` unless the caller passes `historyComplete:true` (a present snapshot cannot prove no past item vanished). Any unconfirmed/partial item or conflicting duplicate timestamp also forces `partial`. No timestamps at all => `unknown`.
- Dedup by `work_id`; a standalone session whose id is in a mission's `session_ids` (no conflicting host) is dropped (reassociation).
- `attention_needed` = blocked | review | failed with `updated_at` in the window (approximation, snapshot).
- Timestamps without a zone offset are treated as missing.

## Server gaps (NOT built)
1. No cross-entity windowed event query: events are readable only per entity (`entity_type`+`entity_id`), so a week of started/finished missions cannot be derived without N calls; no `since/until` filter.
2. `intel_bridge` stores no mission/session lifecycle events, so no durable history of completions.
3. Missions in the snapshot that were deleted/rotated out are invisible, hence `historyComplete` must be proven by a future server endpoint (e.g. missions with `started_at`/`completed_at` in `[start,end)`).
4. Session completion timestamps are not carried into WorkSummary (sessions never complete missions anyway).
