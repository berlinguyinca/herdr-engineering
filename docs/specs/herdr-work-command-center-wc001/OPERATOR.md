# Work Command Center: operator guide (WC-001 to WC-006)

Status: code complete on branch `feat/wc001-s6-validation-rollout`; **nothing is deployed**. No production coverage has been observed; everything below describes what the code does, verified against fixtures and the fixture server only.

## Two-minute walkthrough
1. Open the dashboard Overview (`#/overview`). Under Attention is the **This week** card: five tiles (Started, Finished, Open, Quota-paused, Needs attention) and rows grouped Active / Paused / Completed this week / Unconfirmed.
2. Click a row. A mission row opens the existing mission page (`#/missions/<key>`); an agent that belongs to no confirmed mission opens its session (`#/herd/session/<id>`). One click.
3. On a session page the **Work context** header (above the story) names the parent mission, its measured progress and the other agents of that mission. "Not linked to a mission" means the association could not be proven by ID, not that none exists.
4. The **Terminal** button on the session page shows a copyable `herdr attach ...` command. The browser never opens or focuses a terminal.
5. On **Projects** (`#/github/projects`), a PR card shows **Open in Herdr** only when exactly one mission recorded that exact repository and PR number. Otherwise the card has only its GitHub link.

## Enable, disable, roll back
- Capability name: `work_center_v1`, advertised in `GET /api/v1/health` `capabilities`.
- Enable: set `control_plane.work_center.enabled: true` in the control-plane YAML and restart the control plane. Strict boolean `true` only (`"true"`, `1`, a missing key all mean off). Default is **off**.
- Disable (rollback, no redeploy): set it to `false` or remove the block, restart the control plane. Open dashboards pick it up on the next page load (the probe runs once per load).
- When off, the dashboard has exactly the pre-Work-Command-Center behaviour: no This week card (saved layouts ignore it), no Work context header, no Open in Herdr link, and the board does not read `/api/v1/mission-outcomes`. A failed or slow (over 3 s) capability probe also means off. Covered by `tests/playwright/work-center-e2e.test.mjs` and `work-center-real-server.test.mjs`.
- The server-side additive `prs` field on `GET /api/v1/mission-outcomes` (WC-005b) is always present; with the flag off the dashboard does not read it and no other client depends on it.
- Code rollback: revert the WC-001 to WC-006 commits (all additive; no schema, route or table was removed or changed).
- The flag does not change any permission: the same read endpoints, same credentials, no writes.

## What the numbers mean
- **Started / Finished (G1)**: one read of `GET /api/v1/work/weekly-events` per Overview load (flag on only; no polling) supplies stored started/finished events, merged by work id. The badge reads "at least N (partial) - history from <date>" where the date is the earliest stored lifecycle event (the horizon). "complete" appears only if the server says `coverage.complete:true` for the whole week; this build never does (see Known gaps). If the read fails the card falls back to the snapshot-only numbers and says so.
- **Started / Finished (snapshot fallback)**: missions with a recorded timestamp in the current Monday-to-Monday week (the chosen time zone, default browser; week start default Monday). They are lower bounds: the card says "at least N (partial)" because the server has no weekly history, so work that left the snapshot cannot be counted. "unknown" with a dash means no timestamps exist at all; it is never shown as 0.
- **Open / Quota-paused / Needs attention**: snapshots of right now. Quota-paused counts only missions whose status says quota. Needs attention is blocked, in review or failed with an update this week (approximation).
- **Coverage words**: *complete* = every source loaded and nothing ambiguous; *partial* = a source is missing/failed or something was ambiguous, so the number is a lower bound; *unknown* = no evidence, no number is shown.
- **Unconfirmed** group: the report is stale, disconnected or only recorded, so the state may have changed.
- **Progress bar**: only appears when the mission reports measured evidence (acceptance criteria, else weighted DAG), through the existing `measuredProgress`. An agent finishing never completes its mission and never produces a bar or a 100%.
- A mission with many agents is one row; an agent without a provable mission is its own row marked as not linked.
- The card lists at most 5 rows per group; a **Show all N** button (aria-expanded) lists the rest and **Show fewer** restores the cap (G5, per group, kept only until the page is reloaded).
- **Filter chips (G5)**: Started, Finished, Open, Paused, Needs attention (aria-pressed buttons; press again to clear). A chip only chooses which rows are listed, using the same rules as the matching headline count. It never changes the five headline counts, the coverage badges or the partial banner. The **Unconfirmed** group is never filtered out (its state is unknown, so no metric can exclude it) and the card says so while a filter is on. Started/Finished chips list only rows that carry their own recorded timestamp in the week, so they can list fewer rows than the headline when that count comes from stored history.
- **Row details (G5)**: each row has a Details button (aria-expanded) showing only fields the work summary already has: status, coverage, started/finished/updated times in the chosen zone (only those that exist), evidence entries with their times, and links to the Herdr mission detail and session pages. If a verified pane is recorded it points to the session page's copy-command Terminal button; the browser never opens a terminal.
- No repository filter: work summaries carry no repository field and Herdr does not infer one.

## Known gaps
- Weekly history (G1): `GET /api/v1/work/weekly-events?since=&until=&limit=&after=` reads the in-memory event streams (same source and auth as `/api/v1/events`; 404 when the flag is off; max 31-day span, limit max 500). It cannot prove completeness: start events are written when the control plane first sees the work (not the true start), the durable Postgres sink is best-effort and not retried, and work that never ends has no finish event. So `coverage.complete` is always false here, Started/Finished stay "at least N (partial)", and the banner stays visible. Quota-paused history is not emitted by any Python code, so no paused_quota events exist yet.
- Issue cards (G8): an ISSUE card shows Open in Herdr only when Pi's snapshot contract v4 explicitly links that exact repository+issue number to exactly one mission (`links: [{kind:'issue', ...}]`, served as `issue_refs` on `GET /api/v1/mission-outcomes`). Two missions carrying the same issue is ambiguous (no link). Titles and `Closes #N` text are never read. Until a Pi build that emits v4 links is deployed, every issue card still has only its GitHub link (see handoffs/G2.md, handoffs/G8.md).
- PR links (G3): `GET /api/v1/mission-outcomes` now also returns top-level `pr_refs` ({mission key: [{repository, number}]}) for every listed mission, running included, so a PR recorded by a running mission verifies. The board reads refs on mount and re-reads them on its existing refresh cycle (5 s poll / live event / tab return), at most once per 30 s; no new timer. A PR still only verifies once Herdr has recorded it against the mission (a mission-reported PR record); nothing is guessed. Older servers without `pr_refs` fall back to ended missions only.
- Week time zone and first day (G4): the card has a Time zone select and a Week starts select (Monday default, Sunday, Saturday). Choices are stored per browser in localStorage key `herdr.overview.week.v1` (not per user or synced across devices; no server store was suitable, see handoffs/G4.md). Unknown zones fall back to the browser zone; unknown week starts to Monday; blocked storage means the choice lasts for the page only. Changing either re-reads the weekly history for the new window.
- Terminal attach is copy-command only.
- Saved Overview layouts place This week last (new cards append to a saved order) until the user moves it.
- Two recorded missions that share one id and no source are keyed together by the existing mission catalog; a Work context link to such a mission is labelled "not fully confirmed" rather than hidden.
- Pi-reported next action (G8): the session Work context and the week-card row Details show `Pi-reported next action` only when the mission's Pi snapshot carries non-empty `nextAction` text (with its time when given). Pi's literal `No further action is scheduled`, empty text or an absent field show nothing. It is never inferred, and sessions without a mission never show one. The mission live view uses the same rule (G9): the literal, empty text or an absent field show no Next action row.
- Pi snapshot contract v4 (G8): the feed accepts contractVersion 3 and 4. v4 adds optional `created_at`, `completed_at` and `links` per mission. Pi times appear only as Details evidence entries (`pi_reported_created`, `pi_reported_completed`); they never set Started/Finished, never complete the history, and never change coverage. Pi PR links join the PR refs of running missions (deduped with Herdr's own PR records). No inline issue/PR link inside the Work context header.
- Pi snapshot reader (G9): `pi_snapshot.py` (CLI converter) now also accepts contractVersion 4, mapped exactly like v3 (it never carried times or links; the feed does). Confirmed against Pi's real v4 golden: `created_at`, `completed_at`, `links` sit on each `missions[]` entry. Verified end to end from that golden shape through the feed and server to `issue_refs`/`pr_refs`; not yet against a live Pi build (see handoffs/G9.md).
- Durable Pi activity (G8): the Pi activity projection (the data behind Work context, next action and live view) is now mirrored to the existing durable event store as a private `mission_activity_store` stream, so a control-plane restart no longer empties it. Same caps as before (128 missions, 24 h, 128 KB each); writes are throttled to one per 30 s per mission (a connection change writes at once), so a restart can lose up to the last 30 s of change. G9 ran write, restart, read and 24 h prune against a real throwaway PostgreSQL 16 (not production). Expired and corrupt rows are skipped on start. No new table or migration.
- Expansion, filter and details state (G5) is in memory per page only; a reload resets it. No repository filter until the work summary carries a repository (see handoffs/G5.md).
