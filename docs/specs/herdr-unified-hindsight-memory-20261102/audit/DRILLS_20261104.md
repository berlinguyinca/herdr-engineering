## 1. Outage: container stop / start (readiness #5, first scenario)

`herdr-control-plane.sh -p hindsight stop` → `start` → `wait-ready`.

| Observation | Evidence |

## 2. Process crash: SIGKILL of the memory container

`kill -9 <container-init-pid>` (engine reports `exited (code: 137, KILLED)`), then
`herdr-control-plane.sh -p hindsight start`.

**2a. Writes already acked `queued_durable` before the kill.** 20 writes queued, then SIGKILL,
then restart:

- Before restart: `{"pending": 20, "delivered": 0}` — durable in SQLite, no data loss.
- After restart + `sync`: `{"delivered": 20, "pending": 0}`; **20 of 20** notes recallable.
- Re-running `sync`: `{"delivered": 0, "pending": 0}` — idempotent replay.
- Duplicate check: one probe note retained twice with the same document id →
  `{"state": "queued", "outcome": "queued_durable"}` then `{"state": "delivered", "outcome": "persisted"}`
  → **1 server copy, 1 recall hit** (no duplicate facts).

**2b. Writes in flight during the kill.** 20 in-flight writes at kill time: after restart the
outbox was empty (`pending: 0`) with **0** of the 20 recallable, and `delivered` stayed **0**.
Those writes were never acked as durable, so no loss is claimed — but see **D19**: the queue is
silently emptied without an accounting row, so this case cannot be distinguished from success by
later inspection.

## 12. Defect found while re-running: the queue is keyed by server address

After the outage drill, `outbox` held one row (`seq 128`, `drillv2-probe`) while `status` reported
`pending: 0`. `identity` and `namespace` hash the configured `base_url`, and the drill had changed
that address — so both hashes moved and the row became invisible to `counts()` and unreachable by
`sync()`. Filed as **berlinguyinca/herdr-memory#5**, fixed by **berlinguyinca/herdr-memory#6**:
ownership is now the credential plus the row's own provenance (project/harness/bank), with an
`aliases` record of every address a database has been opened with.

Verified live with the PR build in an isolated venv against that stranded row: it was counted,
adopted and acknowledged (`acknowledgements` 220 → 221, `outbox` 1 → 0). **D19 closed in #6** — merged as
`89a8529`, promoted to `0.1.3` on both hosts, and re-verified on the shipped build in §11.1. The ledger
half of the same issue is **not** closed; #5 was reopened after its auto-close (§11.1).

Cleaning the drill rows exposed a second gap: recall results in the contract-v1 shape carry a
server `memory_id` and **no** `document_id`, so `forget` cannot address them — cleanup needed
`GET /documents?limit=1000` + `DELETE /documents/{id}` by hand. Filed as
**berlinguyinca/herdr-memory#8** (**D20**). All 28 synthetic documents in `canary-facts` were then
deleted and the bank re-verified empty; recall returns `[]`; `status` reports
`healthy: true, pending: 0, reason: null`.

## 14. What the harness actually remembers (2026-11-04)

The operator's question was concrete: **what does Pi remember?** It was unanswerable, and not
because memory was empty.

### 14.1 Reproduced: recall was unreachable, not empty

From `~/IdeaProjects` on the Mac - a real working directory, and where Pi sessions start:

```
$ herdr-memory --harness pi status
{"error": "Current directory has no configured project; use --project"}
$ herdr-memory --harness pi recall "fleet update memory promotion" --scope global
{"error": "Current directory has no configured project; use --project"}
$ herdr-memory --harness pi recall "…" --scope project
{"error": "Current directory has no configured project; use --project"}
```

From one of the two directories listed in `projects.canary.paths`, the same calls answered
normally (`"project": "canary", "healthy": true, "auth_ok": true`). Prefix matching inside a
mapped root already worked, so the gap was exactly "outside every mapped root" - and the
installed Pi skill tells the harness to run `recall`/`retain` from wherever it is working.

Cause: `cli.resolve_project()` matched only `--project` and `projects.*.paths`, and the
documented `default_project` fallback **was never implemented**
(`grep -rn default_project src/` → nothing). Filed as
[herdr-memory#10](https://github.com/berlinguyinca/herdr-memory/issues/10), fixed in
[herdr-memory#11](https://github.com/berlinguyinca/herdr-memory/pull/11) (client **0.1.4**,
merged and promoted to both hosts): resolution is now `--project` → longest path match →
`default_project`, the default must name a configured project (typo → fail closed before any
cache directory is created), and mapping keeps priority.

Operator configuration, both hosts (`default_project` set to the only configured project,
`canary`; backups at `config.json.bak-20261104-default-project`). This is a deliberate choice
the operator owns: whatever `default_project` names is the tenant that receives notes from
unmapped directories.

### 14.2 The retention gate is real, and it rejects

```

{"error": "Durable facts require explicit save intent or evidence references", "outcome": "rejected"}
```

file; why `doctor` must pass both `--project` and `--harness`). Each answered
`{"state": "delivered", "outcome": "persisted", "bank_id": …, "revision": 1}`.

### 14.3 Recall works, from wherever the session is

From `~/IdeaProjects` (unmapped), `--scope global` for *"why does the nightly fleet update fail
on bender"* returned 3 results, top hit the fleet-update unit fact; `--scope project` for

So: memory was never unreachable by design, only by an unimplemented config key. It is now

ambient conversation is not captured, which is the design's intent rather than a gap.

### 14.5 What the ledger actually claims (client `0.1.5`)

"Pi remembers X" is only true if the service accepted X, and until `0.1.5` the client could not say
whether it had (D25). The three defects the drills turned into fixes were all read out of the same
place - the queue's schema, its `INSERT`, and live HTTP - rather than reasoned about from the design:

```
GET /v1/default/banks/canary-facts/documents/mem-096e5bef8b0f2a3ae258d5abe29e0074507f077f -> 200
GET /v1/default/banks/canary-facts/documents/drillv2-probe                              -> 404 {"detail":"Document not found"}
GET /v1/default/banks/canary-facts/documents?limit=1000
  items[].id = "mem-..." and document_metadata.memory_id = "mem-..."   # the server overwrites the id we sent
```

So D20's premise was wrong on this deployment: `/documents` exposes only `mem-...` ids, which is why
`0.1.5` stores both forms and publishes the one that resolves as `address`. A write stranded under
another identity now shows as `unconfirmed` with `ledger_discrepancies` and makes `healthy: false`;
before, the same state read as `verified` with `pending: 0`. See
[herdr-memory#12](https://github.com/berlinguyinca/herdr-memory/pull/12) for the tests (queue-time
status, stranded write never reading back as `verified`, dead-letter as `undelivered`, retraction
outranking an outstanding write, both id forms, `documents` pagination, config validation).
