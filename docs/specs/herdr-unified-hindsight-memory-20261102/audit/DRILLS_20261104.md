## 1. Outage: container stop / start (readiness #5, first scenario)

`herdr-control-plane.sh -p hindsight stop` → `start` → `wait-ready`.

| Observation | Evidence |
| --- | --- |
| CLI reads during the outage | exit 0, `offline: true`, `degraded: true`, `error: "Memory service unavailable (HTTP 503)"`, `results: []` |
| `recall-context.ts` engine hook during the outage | **112 ms**, 0 bytes, exit 0 (fails open inside Pi's 250 ms budget) |
| Writes during the outage | `{"state": "queued", "outcome": "queued_durable"}` — durable in `~/.local/state/herdr-memory/delivery.sqlite3` |
| Recovery | `herdr-memory sync` → `{"delivered": 1, "pending": 0}`; the queued note became recallable |
| No queue growth while the service was down | `pending` stayed at the single queued row |

## 2. Process crash: SIGKILL of the memory container

`kill -9 <container-init-pid>` (engine reports `exited (code: 137, KILLED)`), then
`herdr-control-plane.sh -p hindsight start`.

**2a. Writes already acked `queued_durable` before the kill.** 20 writes queued, then SIGKILL,
then restart:

- Before restart: `{"pending": 20, "delivered": 0}` — durable in SQLite, no data loss.
- After restart + `sync`: `{"delivered": 20, "pending": 0}`; **20 of 20** notes recallable.
- Re-running `sync`: `{"delivered": 0, "pending": 0}` — idempotent replay.
- Duplicate check: one probe note retained twice with the same document id →
  `{"state": "queued", "outcome": "queued_durable"}` then `{"state": "delivered", "outcome": "persisted"}`
  → **1 server copy, 1 recall hit** (no duplicate facts).

**2b. Writes in flight during the kill.** 20 in-flight writes at kill time: after restart the
outbox was empty (`pending: 0`) with **0** of the 20 recallable, and `delivered` stayed **0**.
Those writes were never acked as durable, so no loss is claimed — but see **D19**: the queue is
silently emptied without an accounting row, so this case cannot be distinguished from success by
later inspection.

## 3. Bad model directory

`~/.local/share/herdr-memory/models/<id>/onnx` moved away, service restarted, then restored.

- With the model absent: server comes up but reports `unhealthy`; reads **fail open**
  (exit 0, empty results, `error: "Memory service unavailable (HTTP 503)"`); writes queue
  (`outcome: queued_durable`); `doctor` reports `server: fail` / `server reports unhealthy`.
- After restoring the directory and restarting: queued writes deliver (`{"delivered": 1, "pending": 0}`)
  and writes return `persisted` — no manual repair beyond restoring the asset.

## 4. Queue pressure (bounded)

10 then 30 concurrent `retain` calls while the worker pool was saturated
(`HERDR_MEMORY_WORKERS=2`, `HERDR_MEMORY_QUEUE_SIZE=8`, queue depth observed 6–7, 25% utilization):

- 10 concurrent → `{"delivered": 10, "pending": 0, "dead": 0}`, all 10 recallable.
- 30 concurrent → `{"delivered": 30, "pending": 0, "dead": 0}`, all 30 recallable, no duplicates.
- While saturated, reads stayed fail-open and `pending` never exceeded the issued count.

## 8. Defects recorded by these drills

Numbering continues `audit/HARNESS_INSTALL_20261103.md` (D1-D12), no gaps.

| ID | Sev | Defect | State |
| --- | --- | --- | --- |
| D13 | **P1** | `status`, `doctor` and `herdr-eng memory doctor` reported `healthy: true` / `OK server reachable` while every authenticated read and write returned HTTP 401: health was `/health` reachability, and `/health` answers without a credential. | Fixed in [herdr-memory#3](https://github.com/berlinguyinca/herdr-memory/pull/3); live-verified on bender. Production install still on the old build until merge + promotion. |
| D14 | P2 | A refused credential kept serving cached reads, and harness reads failed **closed** (exit 1, no `offline`/`degraded` shape) instead of degrading. | Fixed in #3: refused scope's cache rows are deleted (including rows written under a different credential *file*, which is how revocations land) and fail-open callers get `degraded: true, error: "auth_rejected"`. Live-verified: cache rows 1 -> 0. |
| D15 | **P1** | `sync()` never fired from another operation, so writes acknowledged `queued_durable` during an outage stayed in `delivery.sqlite3` until someone ran `herdr-memory sync` by hand — `herdr-eng memory status` kept reporting the outage long after recovery. | Fixed in #3: `recall` and `status` drain within a bounded budget (free when empty; skipped when the credential is refused). Live-verified: `pending: 1 / dead_letter: 1` returned to `0 / 0, healthy: true` from a plain `status`. |
| D16 | P2 | Writes issued while the credential is refused were retried three times and parked to `dead_letter` (`dead: 1`) on the old build. | Mitigated in #3 (401/403 is now `Rejected`, such writes are not queued). Upstream still needs a decision on the operator-visible outcome for a refused write. |
| D17 | P2 | Writes in flight at SIGKILL were removed from the durable outbox during replay with **no** `dead_letter`/`delivered` accounting (20 writes vanished silently), so "never delivered" cannot be distinguished from "delivered" after the fact. | **Open.** Needs an explicit attempt-outcome record per queued operation (and probably a server-side idempotency key). |
| D18 | P2 | Neither `herdr-memory doctor` nor `herdr-eng memory doctor` could report the installed client version/revision (`UNKNOWN package_revision  installed herdr-memory revision not determinable`) — the reason D7 stayed hidden for a day. | Fixed in #3 (`herdr-memory --version` reports client **and** contract; `doctor()` includes `client_version`). `herdr-eng` still needs a contract probe rather than a pin comparison. |
