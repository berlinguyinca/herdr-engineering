## Flag and rollback
Fleet config `control_plane.architecture.enabled: true` (strict keys; default off ⇒ routes 404, no `architecture_v1` capability, and the Architecture nav tab is hidden; a direct link shows an explanatory empty state). Explain is a separate opt-in.

**Restart required.** The whole `control_plane.architecture` section is read once when the control plane starts (it is listed in `RESTART_REQUIRED_KEYS`): changing `enabled`, `explain`, `cache`, `request_ttl_seconds`, `agent_hosts` or `require_host_binding` takes effect only after a restart. A bad value (unknown key, non-boolean `enabled`, out-of-range integer, unreadable `explain.api_key_file`, an `agent_hosts` entry that names no agent-role key, a non-boolean `require_host_binding`) makes startup fail with a message naming the key; it is never silently ignored.

```yaml
control_plane:
  architecture:
    enabled: true
    request_ttl_seconds: 3600        # an unclaimed `requested` analysis expires after this (60 s .. 7 d)
    cache:                           # loaded graphs: LRU, re-read from the artifact store on demand
      max_graphs: 8                  # 1 .. 1000
      max_bytes: 268435456           # stored graph bytes (the parsed form is several times larger)
    agent_hosts:                     # optional: bind an agent API key to the host ids it may act for
      <agent api key>: [bender, beast]
    require_host_binding: true       # recommended in production; default false
```

**Host identity of agent keys.** API keys carry a role, not a host; there is no per-host enrollment. An agent key listed in `agent_hosts` may publish snapshots, claim jobs and report progress only for its hosts (403 otherwise). An agent key that is not listed is trusted to name any `host_id` (pinned by `test_unbound_agent_keys_are_trusted_for_host_id_bound_keys_are_not`) unless `require_host_binding: true`: then every architecture POST (publish, claim, progress/result report) from an agent key with no `agent_hosts` entry is refused with 403 `this API key is not bound to any host (control_plane.architecture.agent_hosts)` (pinned by `test_require_host_binding_refuses_unbound_agent_keys`). **Recommended production setting:** `require_host_binding: true` with one agent key per analysing host, each bound to that host only. It defaults to false so existing deployments keep working. Read-only GETs are unaffected (the role model already allows them). A report naming a different host than the job's own is refused (409) either way.

**Jobs.** A `requested` analysis that no host claims within `request_ttl_seconds` ends as `expired`. Operators cancel any unfinished job with `POST /api/v1/architecture/analyses/<id>/cancel`, or with the **Cancel** button in the Architecture view's *Analysis jobs* list (requested, started and running jobs; asks for confirmation, disables itself while the request is in flight; the view cannot know the key's role, so a non-operator key sees the server's 401/403 refusal as escaped text); a running host sees the cancel on its next heartbeat. `herdr-eng architecture serve` survives an unreachable, restarting or refusing control plane: claim errors back off exponentially (capped at 300 s) and a refused job report is logged, never fatal. **Deploying `serve`:** `deploy/control-plane/herdr-architecture-serve.service` is a hardened systemd user unit (`Type=simple`, `Restart=on-failure`, `NoNewPrivileges=yes`, `UMask=0077`; no timer, since `serve` is a long-running loop). It runs `herdr-eng architecture serve --config ~/.config/herdr-engineering/architecture-serve.yaml` and reads no environment: the YAML file (template `deploy/control-plane/architecture-serve.example.yaml`) carries `url`, `api_key_file`, `host_id`, `checkouts`, `poll`, `timeout` and `cache_dir`; command-line flags override it. Install per analysing host: put the agent key in `~/.config/herdr-engineering/architecture-agent.key` (0600) and bind it in `agent_hosts`, write the YAML, then `cp deploy/control-plane/herdr-architecture-serve.service ~/.config/systemd/user/ && systemctl --user daemon-reload && systemctl --user enable --now herdr-architecture-serve.service`. Like the other control-plane user units it is not installed by any script; `tests/test_deploy_units.py` checks that every unit in the repo parses, that the worker's `ExecStart` is accepted by the real CLI parser, and that no unit outside a frozen legacy list uses `Environment=`/`EnvironmentFile=`. No migration: rollback = set the flag false or revert the branch. Snapshots are rebuilt from events at boot; graph bytes need the artifact blob, so an in-memory-only control plane loses graph bytes on restart.

## Known gaps
1. Call edges are name-resolved only (no type inference, no inheritance); JS/TS symbols come from a scanner, and Go/Rust/Java/etc. have no symbols (a language-server or tree-sitter pass would be next).
2. No `autospec_ref` or authoritative `issue_ref`: no source data exists. Worktree correlation only helps when the analysis host analyses that checkout.
3. Woodpecker is activated, but its gates are red on the agents (see the gate table). Shared choke points `api.py`, `app.js`, `ingest.py` may conflict with sibling worktrees.
