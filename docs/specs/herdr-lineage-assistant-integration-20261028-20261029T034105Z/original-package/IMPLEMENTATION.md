# Herdr Mission Continuity, Agent Lineage & Personal Assistant Integration
Date: 2026-10-28
Status: Implementation-ready integration specification; repository audits and live acceptance evidence required.

## 0. Objective and non-negotiables
Complete and consolidate the existing Herdr/Pi/AutoSpec architecture, never create competing engines. A mission can survive multiple Pi generations, cross-model and cross-host handoffs, parallel Claude feature branches, reviews, CI, artifact production and human/assistant collaboration. The Mission Workbench is a durable visualization and authorized control surface. The personal assistant can observe, explain, propose and safely execute scoped operations using existing authorities. Every generated artifact, issue, PR, review, CI run, plan and decision is inspectable from the graph and timeline after all processes terminate.

## 2. Authority and deployment boundaries
- Pi Engineering: authoritative executing mission/worker attempts, local ledger, validated checkpoint, fencing, worktrees, lifecycle, verification; remains standalone with no Herdr.
- AutoSpec: spec/issue/task dependency DAG, quality policies, reviews/merge eligibility; do not duplicate lifecycle.
- Herdr control plane: authenticated, scoped events, durable graph projection, read-model and safe command gateway; existing collaboration rooms and personal assistant domain. No second task scheduler.
- Herdr terminal/local Pi UI: views and controls backed by the SAME room, mission and agent APIs; not a forked state store. Closing a tab never cancels work.
- Git/GitHub/CI: code, revision, PR, checks and merge truth. The latest SHA invalidates stale review.
- Artifact Studio + existing content-addressed object storage: blobs, versioned artifacts, previews and backlinks; graph holds stable references + immutable revision/hash, not copied blobs.
- OpenViking: shared retrievable project memory, scoped by actor, mission, audience; not authorization or execution truth.
- Tern/InferWeave: optional model routing/capacity; do not assume naming/endpoint or dependency before live config audit.
- Rakazo: optional assistant runtime/mobile client or reusable capability adapter, subject to fit audit; Herdr assistant authorization remains canonical. Absolutely no direct Rakazo-to-agent shell, unrestricted terminal or blanket elevated credentials.

## 3. Canonical mission and lineage contracts
Retain the existing Herdr envelope v2, `docs/contracts/lineage-events.md`, and Pi `LineageEmitter`. No `lineage.v3` unless unavoidable and migrated. Existing node kinds: room, workspace, mission, plan, task, agent, attempt, session, tab, pane, handoff, thread, message, decision, approach, worktree, commit, pr, ci, review, finding, artifact, gate, issue. Existing edge kinds: spawn, handoff, delegation, consultation, dependency, issue_link, fork, supersession, reviewed, produced, validated. Extend **attributes** and projections only when necessary. Distinguish logical agent from worker attempt and model session; rollover is a new session on the same logical agent/attempt where contract requires, new attempt when genuinely resumed/reassigned. Never infer edges from UI/chat text. Event/graph IDs are stable, events deduped and correlated. Keep event ordering, room membership visibility and source provenance. Sensitive cross-tenant graph traversal must fail closed. New assistant actions are linked by existing `thread` / `message` / `decision` and `consultation` / `delegation` / `produced` edges, or a documented compatible extension after audit.

## 4. Automatic continuity protocol
Audit existing checkpoint and `session.rolled_over` logic; patch gaps instead of building parallel hooks. Trigger graceful checkpoint on context budget (defaults as **proposed** thresholds: soft 70%, preferred rollover 80%, emergency 90%; make model/runtime-adjustable), user pause, phase boundary, quota block, process crash recovery and host migration. Context size and quota are DISTINCT causes. A checkpoint contains immutable hashes/URIs, exact Git HEAD/base, dirty/untracked snapshot, repo/worktree ownership, completed/remaining acceptance criteria, successful/failed test evidence, plan decisions, unresolved bugs, next executable action, bounded curated context and memory refs. Verify a checkpoint before revoking source lease, then fence old writers and hand to eligible successor. Handle crashes at each step with idempotent retries and last-known-good state. Never replay entire transcripts or raw secrets into successor context. Do not assume a lease fences a runaway OS process: terminate/quarantine/or isolate. Tests: 10+ sequential handoffs, cross-model and cross-host, 60+ sessions, dropped/duplicate/out-of-order events, crash at all handoff stages, memory/object store outages, concurrent writer prevention, no double merges/emails.

## 5. Branch and quality workflow
Pi builds core -> context handoff Pi -> split Claude feature + Pi continuation in separate worktrees -> independent reviewer on exact SHA -> CI -> repair handoff -> review new SHA -> merge only after gate evidence. Each fork has approach ID, parent and dependency edges, bounded scope, explicit acceptance criteria and owner. Avoid review self-approval and re-review stale SHAs. Track accepted changes, gate failures, cycle/loop rate, handoff success/recovery latency, rework, review precision, issue lead time, test coverage and observed costs/tokens (unknown if unreported). Quality decisions must be evidence-backed, not fabricated scores. Optional A/B comparisons of different decomposition/model choices without weakening gates.

## 6. Mission Workbench UI and local terminal mirror
Extend current Herdr Missions/Collaboration UI: DEFAULT: (a) active agent lineage graph, (b) synchronized time axis, (c) contextual inspector with mission status, blockers, next action, artifacts and PR/CI summary. No 8-pane dashboard by default. Collapsible tabs: history/replay, reviews, evidence, assistant, resource metrics. Graph nodes visually distinguish session, attempt, agent, task, artifact, CI; edge labels distinguish handoff, branch, review and dependency. Drag/pan/zoom, search/filter, focus agent/branch, live vs replay, time scrubber, 100s/1000s event virtualization, accessible keyboard and reduced motion. Click shows linked terminal/worktree when authorized, safe log excerpts, upstream/downstream relationships and verified generated artifacts. Local Pi `/room` or `/mission` TUI attaches via the same authenticated room/workspace/mission APIs; show compact project tree + current agents + attention inbox + message/assign/fork commands, with full graph link to Herdr. Follow existing light/dark tokens and mobile responsive design; small mobile view prioritizes status, attention and approvals. Persist layout preferences separately from mission truth.

## 7. Personal assistant: concrete integration
Use existing `assistant.py` and `personal-assistant-view.js` as the authority and surface; first inventory their actual endpoints, grants, tool implementations, inference runner, routines, delegation and audit behavior. The assistant should be a **mission participant**, not mission owner or scheduler. It can:
A. Read authorized mission graph, lineage history, GitHub/CI/artifact evidence; answer: 'What happened since Monday?', 'why did agent B branch?', 'Which PR failed and why?'. Include links and uncertainty/freshness.
B. Propose tasks/feature branches, route requests to AutoSpec/Pi via existing mission-command API. Require explicit grant; approvals for new scope, code mutation or privileged operations.
C. Watch CI events or eligible scheduled routines: dedupe repeated alerts, diagnose, propose a corrective spec/PR and request independent review; simple auto-merge only through existing policy gates, never by assistant verdict alone.
D. Ingest emails WITH consent via approved Gmail/integration connector: match thread/attachments to repository/issue/mission using deterministic identifiers plus confidence; propose links for ambiguous matches; create a versioned Artifact Studio document with original metadata/provenance and permission scope. Do not silently leak private mail into wider room. Outbound Gmail actions require scoped send grant and explicit approval by default; drafts safe under a scoped draft grant.
E. Ask another Pi/Claude agent for a review using existing delegation command, with bounded budget/time and no shell impersonation.
F. Deliver concise digests in dashboard, local Pi room and mobile/phone; preserve notification preferences and enforce dedupe.
G. Explain model routing choice, artifact provenance, decisions and handoff lineage; may recommend changes to thresholds, but no autonomous quality-policy relaxation.

Implement assistant-to-Herdr adapter using scoped APIs (read graph/timeline/artifact/CI; `request_mission`, `request_review`, `propose_branch`, `draft_email`, `request_send_approval`, `comment_on_node`). These are conceptual operations; map them to EXISTING endpoint names and exact grant policy during Phase 0, and implement only missing thin adapters. Do not invent unverified endpoints. Correlate assistant thread/action/routine/approval IDs to mission and graph IDs in event metadata. Bind each action to authenticated principal, room and mission permissions, idempotency key, request hash, TTL, audit and human-readable dry-run. Assistant model is replaceable and can use optional InferWeave/Tern routing; tool permissions never depend on selected model. External Rakazo app client can connect only through an approved, restricted bridge after auth/session security audit. Keep assistant feature flag disabled until integration tests prove isolation.

## 8. Rakazo integration feasibility/security decisions
Rakazo is beta and offers its own persistent bot layer, app integrations, background routines, PG/Prisma, mobile and Pi. This overlaps Herdr's newly present assistant domain. Adopt only capabilities unavailable or genuinely superior: optional native phone client, voice experience, safe connector adapters. Preferred implementation: Herdr remains authoritative assistant backend; Rakazo is optional UI/voice adapter if its client API can support external backend, otherwise use Herdr mobile/PWA to avoid maintaining a divergent app. Do not claim plug-and-play compatibility until inspected. Investigate: licensing/dependency policy, auth mapping, multi-tenant isolation, OAuth token handling, tool invocation, webhook/event subscriptions, remote computer execution, provenance, message transport, background schedules, secret storage, auditability, stable APIs, model routing, mobile rebranding constraints. Produce `rakazo-fit-gap.md` with reuse/wrap/reject matrix and threats before any deployment.

## 9. Phased execution with hard gates
P0 Audit: clone/fetch actual default branches; read AGENTS.md, existing specs, code & tests; inventory current features, exact SHA, lineage/assistant/room APIs, hooks, adapters, artifact schema, mobile and runtime. Produce `audit.md`, `reuse-map.md`, `rakazo-fit-gap.md`, `architecture.md`, `test-matrix.md`, ADR for assistant ownership. NO broad editing before this.
P1 Vertical slice: real Pi session/rollover -> durable lineage event -> existing Herdr graph/timeline -> inspector -> artifact/review link. Test on real repo + restart/replay, CI. No mock-only completion.
P2 Continuity: checkpoint validation, leases/fencing, recovery and cross-model continuation; integration/fault tests.
P3 Assistant read-only observer: authenticated graph/missions/artifacts/CI summaries in existing personal assistant chat and room; replay/history, scoped permissions, no action grants by default.
P4 Safe assistant actions: proposed work items, review delegation, approvals, draft/email workflow, CI diagnosis with PR, strict command gateway. Verify negative authorization tests and idempotent retries.
P5 Unified web+terminal UX: local Pi room mirror, persistent graph, inspector, artifact browsing, room messages and synchronized review; phone-friendly attention and approvals.
P6 Reliability/quality: realistic multi-branch scenario, replay, crash/partition, large graph performance, screenshot/keyboard/mobile tests; A/B measurement and performance budgets. Generate evidence and operator runbooks.
Each phase: isolated branch/worktree, tests, PR and commit-linked evidence; no direct main changes; retain existing working components and feature flags. If blocked, record exact blocker and leave resumable handoff, not fictitious green status.

## 10. Acceptance scenarios
1. Mission A starts Pi session S1, context rollover to S2, rollover S3. Same logical agent and documented attempt semantics; exact handoff edges visible; state survives restart.
2. From S3, create independent Claude feature branch and Pi next-phase branch in isolated worktrees. Track DAG and separate artifacts; merge via verified gates.
3. Ask assistant 'What did we achieve yesterday?' Receive concise, source-linked answer with latest artifact/PR/CI evidence and missing data clearly marked.
4. Assistant notices CI failure, creates a PROPOSAL, launches authorized diagnosis through Pi only after policy allows, submits PR, gets independent exact-SHA review; gate permits or blocks merge correctly.
5. Email thread with a plot attachment becomes permission-scoped artifact, linked to source conversation and candidate issue only when confirmed; retracted/corrected attachment is versioned.
6. An unauthorized mobile user cannot read graph or artifact via traversal; even authorized assistant cannot send email or operate a shell without grant/approval.
7. Local Pi room and Herdr show same lineage, including host move. Closing UI does not stop agents.
8. Replaying duplicated/out-of-order source events yields deterministic graph and no duplicate work, emails or merges.
9. 10+ handoffs and 60+ sessions remain inspectable with bounded render and reliable recovery.
